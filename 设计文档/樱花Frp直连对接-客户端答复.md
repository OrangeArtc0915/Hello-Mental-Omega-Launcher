# 答复《樱花Frp直连对接.md》—— 客户端侧选型与设计

> 面向写那份文档的人。你们的约束我们照单全收，下面是 P0 的选型结论和 A 的设计。

## 0. 结论

**选 A：客户端把游戏 UDP 塞进已有那条 TCP 隧道。**

- **B 排除**：客户端内置穿透/内置 EasyTier-n2n，与 HMOL 已经做好的虚拟局域网能力重复，
  且一劳永逸的同时也意味着"以后都不用樱花 Frp"，与你们把它做成产品功能的意图冲突。
- **C 保留为兜底**：EasyTier / n2n 那条今天就能打，客户端零改动。
  建议就在界面上明说：**"要稳就用虚拟局域网；樱花 Frp 直连是实验特性（可能卡顿）"**。

## 1. 你们给的约束（我们确认接受）

| 约束 | 我们这边 |
|---|---|
| 只开一条隧道：TCP → 本机 1233 | ✅ 收到，方案按这个设计 |
| 复制裸 `IP:端口`、不发 `/ip` 前缀 | ✅ 已支持；地址框可直接 Ctrl+V，回车即连 |
| **不写 `lanip.txt`** | ✅ 那条特性我们留着但不依赖它（写了也会被消费，不写完全无影响） |
| 不加第二条隧道、不做 UDP 承载、不装虚拟网卡 | ✅ 全部由客户端自己承载 |
| 实测：能进大厅、能看到玩家列表 | ✅ 与我们这边一致，说明直连那段已经没问题 |

## 2. 为什么 A 是唯一路（同意你们的论证）

你们指出的关键点我们复核过，成立：

- `spawn.ini` 的 `[OtherN] Port` 来自 `LANPlayerInfo.Port`，**局域网下写死 1234**；
- 樱花 Frp 给的是**随机公网端口**，隧道指向本机 1233 → 就算再开一条 UDP 隧道也对不上；
- 所以**游戏内那段只能由客户端自己承载**。

## 3. A 的设计（客户端侧）

### 3.1 数据面：每个对端一个本地端口

不改游戏、不碰 gamemd，只改 `spawn.ini` 的落点：

| spawn.ini 字段 | 局域网原值 | 改造后 |
|---|---|---|
| `[OtherN] Ip` | 对端地址（隧道地址） | **`127.0.0.1`** |
| `[OtherN] Port` | `1234` | **`12340 + N`**（N 就是 `[OtherN]` 的序号，**从 1 开始**，所以是 12341、12342…；最多 8 个 → 12341~12348） |
| `[Settings] Port` | `1234` | 不变（游戏自己接收用） |

> 序号必须 1-based：原版客户端给 `spawn.ini` 的段名是 `[Other1]`、`[Other2]`…
> （实测证据：`[Other1] Name=Snow_ Ip=127.0.0.1 Port=12341`）。写成 0-based 会整体差 1，包全部落空。

于是：

```
gamemd ──发给 127.0.0.1:1234x──▶ 本地中继 ──封装──▶ 经 TCP 隧道 ──▶ 对端中继 ──▶ 注入对端 gamemd 的 1234
                                                                     （源端口仍是 1234x，与对端 spawn.ini 一致）
```

**关键点**：对端回包时，中继也**用同一个 1234x 端口**把包回注给本机 gamemd，
这样 gamemd 看到的源地址 = 它 `spawn.ini` 里写的地址 → **不会被当成陌生来源丢掉**。

### 3.2 承载：**复用大厅那条 TCP 连接**（已按这个实现）

关键结论：**中继不新增任何连接、任何端口，全程只走你们那一条隧道的 1233。**

原因是：客机与房主之间本来就有一条 TCP 连接（进大厅时建立的 JOIN 连接，
它本身就走 1233 隧道），**中继直接把游戏 UDP 封帧塞进这条连接**：
帧格式 `MO-RELAY \u0001 <tag> \u0001 <base64>`，和大厅既有消息共用同一条流、
共用同一套分界规则。所以：

```
gamemd ─UDP→ 127.0.0.1:1234x ─┐
                             │ 封成 MO-RELAY 帧
大厅聊天/选项 ────────────────┴─→【同一条 TCP 连接】─→ 隧道(1233) ─→ 房主
                                                                      │
                                   房主按目标分发（2 人直接转发；3 人以上经房主中转）
                                                                      ↓
对端中继 ─解帧→ 从 1234x 注入 ─UDP→ 对端 gamemd:1234
```

**代价**：游戏的 UDP 现在和聊天共用一条 TCP，会有队头阻塞（下节风险表里那条）。
**收益**：完全符合你们"只开一条隧道"的约束，且不必去动大厅的 accept 逻辑
（原稿里写的"中继自开一条 TCP + 房主侧识别 magic 头"那种做法**没有采用**）。

#### 3.2.1 实现细节：那条连接到底是哪一个（踩过的坑）

"复用大厅那条 TCP"落到代码上有个关键前提：**客机得能拿到那条连接的对象**。

- 大厅类里真正持有连接的是字段 **`LANGameLobby::client`**（`System.Net.Sockets.TcpClient`），
  由 `LANGameLobby::SetUp(bool isHost, IPEndPoint, TcpClient)` 赋值：
  - **房主**：`SetUp` 里自建 `new TcpClient()` 连自己的 `127.0.0.1:1233`；
  - **客机**：`SetUp` 直接保存调用方传进来的那个 `TcpClient`（就是带 JOIN 的那条）。
- 而 **`Players` 里的 `LANPlayerInfo.TcpClient` 在客机侧是 `null`**（那是房主侧 accept 出来的对象）。
  早期版本试着用它发，结果 `TcpClient == null` → 每个包被静默丢弃，
  表现为"客机 `已发出帧` 一直涨、房主 `已收到帧` 恒为 0"。

所以最终做法是：**客机在 `SetUp` 时把 `client` 交给中继注册**，中继发往房主的帧一律走这条连接。

另外还有一个**必须在同一处修的并发问题**：游戏帧由中继后台线程写这条流，
而大厅自己的 `SendMessageToHost`（准备状态、聊天、心跳）由另一个线程写同一条流。
两者各自 `GetStream().Write()` 会互相交错、把帧写坏。所以：

- `SendMessageToHost` 的方法体被整体改写成 **`Relay.SendClientLocked(this.client, this.encoding, message)`**，
  与中继的帧写入**共用同一把静态写锁**（`sendLock`），串行化后不会再串包。

另外，大厅类其实有**两个**，各持有自己的 `client`，两个都注册/接线了：

| 类型 | 什么时候用 |
|---|---|
| `LANGameLobby` | 正常加入房间、房主建房（本次实测走的就是这条） |
| `LANGameLoadingLobby` | 加入"已开始的存档局"（`IsLoadedGame()` 分支，直接进读条界面） |

（`SendMessageToHost` 的改写是**语义等价**的：原来也是 `encoding.GetBytes(message + "\u0002")` 然后 `Write` + `Flush`，
只是多了一层 `try/catch`、多了把锁、并且对 `client == null` 不再抛 NRE。）

### 3.3 3 人以上：星型，经房主分发

RA2 是点对点，每对玩家都要通。所以：

- 每个客机与房主之间有一条中继 TCP；
- 客机把包发给房主，**带上目标玩家的标识**；房主查表转发给对应客机；
- 房主自己的 gamemd 也走同一套（房主既是端点也是转发器）。

**先做 2 人版本**，3 人以上作为第二阶段。

### 3.4 落地方式：中继用 C# 编译，不手写 IL

- 中继本体（UDP 套接字、线程、分帧、房主分发）**用 C# 写、编译成 DLL**，
  放进 `Resources\`（同时复制一份到 `Resources\Binaries\`，两处都会加载）。
- 客户端那边只加**六处很小的 IL 补丁**（全部由 dnlib 写入，逐条过栈自检 + JIT 校验）：

| # | 目标方法 | 补丁内容 | 侧 |
|---|---|---|---|
| 1 | `GameLobbyBase::WriteSpawnIni` | `[OtherN] Ip` → `127.0.0.1`；`[OtherN] Port` → `12340 + 序号`；并调用 `Relay.Start(Players, PLAYERNAME, GamePath + "MoLanRelay.log")` | 双 |
| 2 | `LANGameLobby::HandleMessageFromServer(string)` | 消息以 `MO-RELAY` 开头时交给 `Relay.OnFrame("", msg)` 处理，否则原样落回原逻辑 | 客机（收房主的帧） |
| 3 | `LANGameLobby::HandleClientMessage(string, LANPlayerInfo)` | 同上，`fromName` 取 `lpInfo.Name` | 房主（收客机的帧） |
| 4 | `LANPlayerInfo::SendMessage(string)` | 整体换成 `Relay.SendLocked(this, message)`（房主侧写客机，共用写锁） | 房主 |
| 5 | `LANGameLobby::SetUp` / `LANGameLoadingLobby::SetUp` | 插入 `Relay.RegisterHostClient(this.client, this.encoding)` | 客机（拿到通往房主的连接） |
| 6 | `LANGameLobby::SendMessageToHost(string)` / `LANGameLoadingLobby::SendMessageToHost(string)` | 整体换成 `Relay.SendClientLocked(this.client, this.encoding, message)`（共用写锁） | 双 |

> 补丁 #1 里 `Start` 的调用点刻意放在 `WriteSpawnIni`（`[OtherN]` 循环内、直线代码处）：
> `BtnJoinGame_LeftClick` 那类方法里有 try 区域，往里跳会导致 `InvalidProgramException`。
> 补丁 #4 之所以要动，是因为房主的"聊天"和"游戏帧"共用同一条流，必须共用一把写锁。

## 4. 风险与前提（先说清，避免后面扯皮）

| 风险 | 说明 |
|---|---|
| **TCP 承载 UDP 的延迟/队头阻塞** | RA2 锁步对延迟敏感。走 TCP 中继**可能卡顿**，尤其网络抖动时。这是方案固有代价，不是实现问题。 |
| **双方都必须用打过补丁的客户端** | 中继是客户端行为，一方没补丁就连不起来。 |
| **我这边无法做最终验证** | 我只能验证 IL 合法 + 客户端启动不崩；"两台机器真能打完一局"必须你们/玩家实测。 |
| **3 人以上复杂度陡增** | 房主分发 + 目标标识，建议第二阶段再做。 |

## 5. HMOL 需要做什么

**技术上一件都不用做** —— 完全符合你们"不再加隧道、不写文件"的约束。

唯一建议（产品层面）：

- 在樱花 Frp 那个界面加一句提示：**"该模式为实验性，网络抖动时可能卡顿；要稳请改用 EasyTier / n2n"**；
- 隧道照旧：TCP，公网端口 → 本机 1233。

## 6. 现状：A 已实现，**2 人局实测通过**（读条正常、能进游戏）

按上面第 3 节的设计做完了，**HMOL 依然一件都不用做** —— 隧道照旧 TCP、公网端口 → 本机 1233。

**客户端侧改动（都在 `Resources\` 里）：**

| 文件 | 作用 |
|---|---|
| `MoLanRelay.dll`（新增，同时放一份到 `Resources\Binaries\`） | 中继本体：本地 UDP 端口对、封帧、按方向分发、共用写锁 |
| `clientdx.exe` / `clientogl.exe` / `clientxna.exe` | 第 3.4 节表里那六处 IL 补丁 |

**怎么测（两边都要用打过补丁的客户端）**

1. 主机：HMOL 开隧道 → 客户端进大厅 → 创建房间 → 开始游戏
2. 客机：地址框粘 `IP:端口` → 回车 → 进大厅 → 准备 → 开始
3. 看两边游戏根目录的 **`MoLanRelay.log`**，关键行：

   ```
   ======== MoLanRelay v2026-10-04.4 ========            ← 三台机器必须都是同一个版本号！
   载入的 DLL: D:\...\Resources\MoLanRelay.dll           ← 实际加载的是哪个文件，直接看这行
   register host client: connected / 127.0.0.1:xxxxx     ← 客机拿到通往房主的连接（缓冲后补写）
   start: self=nightfall01 host=False (byOrder=False byConn=False) 玩家数=2 本机端口表=[mmm→12341 ]
   端口映射: mmm→12341
   peer[1] mmm listening 127.0.0.1:12341                 ← 本地 UDP 端口已就位
   第一次收到本机游戏发出的包（来自 127.0.0.1:1234，长度 71）
   第一次收到对端帧（来自 mmm，tag=…，长度 71）
   stats: 本机游戏发出的包=… 已注入本机游戏=… 已发出帧=… 已转发帧=… 已收到帧=… | 分对端: mmm(收12/注13)
   ```

> **排查第一步永远是看第一行的版本号**：三台机器只要有一个是旧版，就会出现
> "那台能收不能发 / 明明是它发的却没到对面"这类现象（旧版没有 3.2.1 里
> `RegisterHostClient` + `SendClientLocked` 那次修复）。若版本号不一致，
> 让那台机器重新覆盖安装包里的 `Resources\MoLanRelay.dll` 和 `Resources\Binaries\MoLanRelay.dll`。

**验收口径**：两边 `stats` 里 **`已发出帧` 和 `已收到帧` 都持续上涨**（差距在个别包以内），
就说明双向中继都通了 —— 此时读条会正常推进。

**3 人以上怎么判**（这几个字段就是为它加的，出问题一眼能定位到是哪一段）：

| 字段 | 含义 / 怎么读 |
|---|---|
| `host=True/False (byOrder=… byConn=…)` | 房主判定用了两个独立信号，**任一成立即算房主**：`byOrder`＝玩家表第一个是不是自己；`byConn`＝所有对端的 `LANPlayerInfo.TcpClient` 都有值（房主侧才有）。两者不一致通常说明玩家表顺序异常，不影响功能，但值得记一笔。 |
| `本机端口表=[名→端口 …]` / `端口映射: …` | 每个对端对应的本地 UDP 端口。**两边应该都能看到同样的一串名字，只是自己的那份映射里不含自己**。任何一边少了一个名字，就是那一方这一路不通。 |
| `分对端: 名(收X/注Y)` | 每个对端各自的"从本机游戏收到 X 个包 / 注入本机游戏 Y 个包"。三人局里如果 `zzz` 一直是 `(收0/注0)`，就说明和 zzz 那一路断了。 |
| `发送失败=N` | 帧在发送时被丢掉的数量（连接为空、已断开、找不到目标玩家等）。**正常应该是 0 或者极少数**；持续上涨一定会在日志里留下一条带原因的 `WarnOnce` 行（每个原因只打一次，不会刷屏）。 |
| 房主侧 `已转发帧` | 房主替客机之间中转的帧数。三人局里这个值应该 > 0；恒为 0 说明客机之间还没有互相发过包。 |

卡住的话把两边的 `MoLanRelay.log` 发出来即可定位。

**验证边界**：IL 已过 dnlib 栈自检 + JIT 校验 + 客户端启动冒烟（无崩溃）；
2 人局已由实测确认走通。3 人局首次实测时，主机日志里 **`已转发帧` 正常增长、按 tag 转发到目标客机**
（见 3.3 星型），转发逻辑本身工作正常；那次失败的根因是**其中一台客机跑的是旧版 DLL**（3.2.1 的修复没打上），
表现为"它发的帧一帧都没到主机、主机也就没东西可转给第三人"，从而锁步卡死。
所以 3 人以上请务必确认三台机器版本号一致。

**保留的判断**：TCP 承载 UDP 有队头阻塞代价，网络抖动时可能卡顿。
如果实测手感不行，就说明这条路只能当兜底 —— 主力还是虚拟局域网（EasyTier/n2n）。
