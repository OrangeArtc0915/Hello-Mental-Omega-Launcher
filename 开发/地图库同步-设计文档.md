- 状态：**设计稿（未实现）**

## 1. 背景

现有「地图同步」是**单张、一次性、无状态**的：

- 房主只能推「当前选中的那一张图」，客机只能要这一张
- 客机不知道自己的地图库和房主差多少
- 中断就得整个重传
- 覆盖/删除后没法回滚
- 客机本地改过的同名图会被直接覆盖

目标：把同步粒度从「一张图」提到「一个地图库」，用 Git 的核心思想
（**内容哈希 + 清单 + 基线 + 差异**）来做增量同步与回滚。

### 1.1 现有实现要点（改造时基于这些）

| 位置（MoLanRelay.cs） | 作用 |
|---|---|
| `MapHelloKind/MAPREQ/MAPDATA/MAPEND/MAPASK/MAPMISS` | 现有单图同步的 6 种消息 |
| `const char MapField = '\u0001'` | 负载内字段分隔（**不能用 `\u0002`**，那是客户端分帧符） |
| `MapChunkBytes = 512`、`MapChunkDelayMs = 6` | 每帧 512 B、间隔 6 ms（base64 后约 700 字符/帧） |

## 2. 目标与非目标

### 目标
1. **多图**：一次比对/一次同步整库或选中的若干张
2. **增量**：已一致的文件不传（按 SHA-256）
3. **可回滚**：客机能恢复到同步前，房主能回到旧版清单
4. **冲突可见**：客机本地改过的文件不会被静默覆盖
5. **断点续传**：断线重连后从缺口继续

### 非目标（明确不做）
- 分支 / rebase / staging（对地图同步无价值，只会加复杂度）
- objects 目录（地图动辄上百 MB，不存第二份 blob）
- 远程仓库/多人协作式提交（这里只有「房主的库」一个权威源）

## 3. 术语映射

| Git | 本项目 | 说明 |
|---|---|---|
| blob | 地图文件本体 | 仍在游戏目录原位，不复制 |
| tree/index | **清单 manifest** | 排序后的 `sha256 + size + path` 文本 |
| commit | **快照** | `{manifestHash, parent, 时间, 作者, 备注}` |
| HEAD | 房主当前指针 | `MoMapRepo\log.txt` 最后一行 |
| index / HEAD（客机侧） | **基线 base** | 上次同步时对方 manifestHash + 本机各文件当时的 sha |
| diff | 三态比对 | base / local / remote |
| checkout | 回滚 | 按备份恢复文件、按清单重写 INI 段 |

`manifestHash = SHA-256(清单文本)` —— 两边比一个字符串就知道是不是同一版。

## 4. 数据模型

### 4.1 清单（manifest）

UTF-8 无 BOM，`\n` 换行，条目按 `path` 序数排序（保证哈希稳定）：

```
<sha256 大写>  <size>  <相对路径，'/' 分隔>  <kind>
A1B2...  2150400  MapsMO/Defend/GuardPresident.map  map
C3D4...    18432  MapsMO/Defend/GuardPresident.png  png
E5F6...     2048  MapsMO/Defend/GuardPresident.ini  ini
```

- `kind ∈ {map, ini, png, other}`；`map` 后缀 `{.map,.mpr,.yrm}`
- 只收「白名单目录」内的文件（见 §10）
- 一张地图 = `kind == map` 的条目 + 同目录同名的附属文件 + INI 里的注册段

### 4.2 快照（commit）

`Resources\MoMapRepo\log.txt`，每行一条（只保留最近 50 条）：

```
<manifestHash>\t<parentHash>\t<yyyy-MM-dd HH:mm:ss>\t<作者>\t<备注>
```

备注自动生成，如「提交 132 张，新增 3，修改 2」。

### 4.3 基线（base）

客机：`Resources\MoMapSyncBase.txt`（**取代**现在的 `MoLanSyncedMaps.txt`，保留旧文件用于迁移）：

```
# 头部
manifest=<对方的 manifestHash>
commit=<对方的快照时间/作者>
# 每个文件在上次同步后的状态
<sha256>  <size>  <相对路径>
```

作用：判断「这个文件是我改的，还是房主改的」。

### 4.4 目录布局

```
<游戏根>\
  Resources\
    MoMapRepo\
      manifests\<manifestHash>.txt     房主：历史清单（最多 50 份，多余的删）
      log.txt                          房主：快照日志
    MoMapSyncBase.txt                  双方：本次同步的基线
    MoMapSyncBase.txt.tmp              传输中的块进度（断点续传）
    MoMapBackup\20261116-201233\...    覆盖/删除前的原文件（保留最近 3 次）
    MoLanSyncedMaps.txt                （旧）单图同步的清单，仅用于迁移
```

## 5. 协议设计

沿用现有通道：大厅那条 TCP，消息格式 `@MO\u0001<kind>\u0001<发送者>\u0001<payload>`，
payload 内字段用 `\u0001`，**整体 base64 + deflate**（文本通道，避免二进制污染）。

### 5.1 新增消息

| kind | 方向 | 负载 | 说明 |
|---|---|---|---|
| `LIBASK` | 客机→房主 | （空） | 请求清单 |
| `LIBDIFF` | 房主→客机 | `manifestHash \| 条目数 \| 条目...` | 分帧发送；条目 = `sha \| size \| b64(path) \| kind` |
| `LIBWANT` | 客机→房主 | `manifestHash \| bitmap` | bitmap = 需要的条目序号（逗号分隔或位串） |
| `LIBDATA` | 房主→客机 | `jobId \| idx \| offset \| len \| crc32 \| b64(data)` | 块传输 |
| `LIBDONE` | 房主→客机 | `jobId \| idx \| 结果` | 单文件发完 |
| `LIBEND` | 房主→客机 | `jobId \| 成功数 \| 失败数` | 整单结束 |
| `LIBPUSH` | 房主→客机 | `manifestHash` | 房主主动推整库（客机据此自动触发 LIBDIFF） |

设计约束（重要）：

- **大消息分帧**：`LIBDIFF` 可能几十 KB，按 ≤4 KB 一片发，片序号写在 payload 第 0 字段
- **块大小**：单图同步现在是 512 B/帧；库同步建议提到 **2048 B/帧 + 4 ms 间隔**（约 4 倍吞吐），
  前提是先在大厅实测不丢帧（丢帧可通过 `LIBDONE` 缺失自动重发该块）
- 兼容：旧客户端不认识这些 kind，会静默忽略；开赛前 3 秒核对会拦住版本不一致的局

### 5.2 块级断点续传

- 客机把「已收到并校验通过的块」写进 `MoMapSyncBase.txt.tmp`：`jobId  idx  offset  len  crc32`
- 重连后客机发 `LIBWANT` 时附带已完成的块位图；房主跳过这些块
- 一个文件全部块到齐 → 拼成 `.mosync-part` → 整体 SHA-256 校验 → 替换原文件 → 从 tmp 中清掉

## 6. 流程与状态机

### 6.1 客机 pull

```
[空闲]
  └─(点「拉取地图库」/ 收到 LIBPUSH)→ [等清单]
        └─ 收齐 LIBDIFF → [比对中]
              ├─ 无差异 → [空闲]（提示「已是最新」）
              └─ 有差异 → [冲突确认]（三态表见 §7）
                    └─ 用户确认 → 发 LIBWANT → [接收中]
                          └─ LIBEND → 校验基线 → 写 INI 段 → 刷新列表 → [空闲]
```

每一步都要有超时（建议：等清单 15 s、单块 10 s、整单 5 min），超时回到 `[空闲]` 并提示。

### 6.2 房主 push

```
[空闲]
  └─(点「推送地图库」)→ 扫描白名单目录 → 生成 manifest → 存快照 → 广播 LIBPUSH
        └─ 各客机自行 pull（房主只回 LIBDIFF / LIBDATA）
```

房主不主动推数据，只「发布版本」；客机拉取与否由客机决定（避免把大厅读线程灌满）。

## 7. 三态比对与冲突

对每个 path，取 base / local / remote 的 sha：

| local vs base | remote vs base | 结论 | 动作 |
|---|---|---|---|
| = | = | 一致 | 跳过 |
| = | ≠ | 房主改了 | 下载覆盖 |
| ≠ | = | 本地改了 | **保留本地**，标「本地修改」 |
| ≠ | ≠（local=remote） | 两边改成一样 | 只更新基线 |
| ≠ | ≠（local≠remote） | **冲突** | 弹窗三选一 |
| 存在 | 无（房主删了） | — | 保留本地，标「房主已删除」 |
| 无 | 有 | 本地缺 | 下载 |
| 无 | 无 | — | 忽略 |

冲突三选一：
1. 用房主的（先备份本地到 `MoMapBackup`）
2. 保留本地的（不覆盖，仅更新基线条目为「本地版本」）
3. 另存为 `<原名>.local.<扩展名>` 后改用房主的

**任何情况下都不静默删除客机文件。**

## 8. INI 注册表处理（`INI\MentalOmegaMaps.ini`）

地图能不能出现在列表里，靠的是：

1. 该地图的注册段 `[MapsMO\Defend\Xxx]`
2. `[MultiMaps]` 段里的一行 `N = MapsMO\Defend\Xxx`

规则：

- 同步新增地图 → 追加注册段 + `[MultiMaps]` 行（复用 `ApplyMapIniSection` / `AddMultiMapsEntry`）
- 回滚/删除地图 → 删注册段 + `[MultiMaps]` 行（复用 `RemoveMapIniSection`）
- 写完统一调 `RefreshMapListAfterSync()` 热刷新；失败则提示「重启客户端」
- 写 INI 前先备份到 `MoMapBackup\<时间>\`，避免手改被误伤

## 10. 安全边界

继承并强化 `WriteMapFile()` 的现有约束：

1. **路径白名单**：只允许写到 `Maps\`、`MapsMO\`、`INI\MentalOmegaMaps.ini` 及其附属
   （`.map/.mpr/.yrm/.ini/.png/.shp/.vxl/.tmp/.aud`）
2. **路径越界**：`..`、绝对路径、UNC 一律拒绝；落盘前比对 `Path.GetFullPath` 前缀
3. **大小上限**：单文件默认 64 MB（可在 `MoLanPatch.ini` 调整 `MaxMapFileMB`）
4. **覆盖前备份**：任何 replace/delete 都先复制到 `MoMapBackup\<时间>\`
5. **只读模式**（可选）：`MoLanPatch.ini` 里 `MapLibReadOnly=1` 时，只比对不落盘

## 11. 性能预算

| 项 | 估算 |
|---|---|
| 清单大小 | 每条约 90 B；500 张图 ≈ 45 KB，deflate 后 ≈ 8 KB，分 2~3 帧 |
| 单图传输 | 2 MB 图，512 B/帧 + 6 ms ≈ 24 s；提到 2 KB/帧 + 4 ms ≈ 6 s |
| 整库首次拉取 | 3.4 GB 不现实 → UI 必须支持「只拉选中的」；首次建议按模式/合集分批 |
| 增量拉取 | 通常 0~3 张图，几秒到几十秒 |

结论：**必须支持选择性子集**，不能默认「整库拉」，否则隧道会跑很久。

## 13. 分阶段实施计划

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **P1** | 多图同步 + 哈希跳过（不引入 manifest 概念，沿用 MAPHELLO 的多文件清单） | 房主一次能推 ≥5 张图；已一致的图不重传（日志跳过数正确） |
| **P2** | manifest + 快照 + 基线 → diff/pull、冲突三选一、本地回滚 | 三态表 8 种情形逐条验证；冲突时弹出三选一 |
| **P3** | 块级断点续传 + deflate + 大块（2 KB/帧） | 传输中断线重连后从缺口继续；同一张图用时明显下降 |
| **P4** | 快照历史/回滚到旧版、导出整库 zip、只读保护 | 能选旧快照并回滚；导出 zip 可再导入 |

每阶段独立可发布，P1 即可解决「一次只能传一张」。

## 14. 测试要点

- 三态表覆盖：8 种组合各造一次（改本地 / 改房主 / 两边都改 / 房主删 / 客机有本地独有）
- 断点续传：传输中拔网线 5 s 再接回；传输中关客机客户端再进房间
- 大图：单张 20 MB 地图 + 500 张库；确认大厅不卡、不丢帧
- INI：同步后列表立即出现；回滚后注册段与 `[MultiMaps]` 都清干净
- 兼容：一台 v0.8.x 一台新版 → 开赛前核对应拦下
- 日志关键字（建议统一前缀）：`maplib:`（清单/差异）、`maplibtx:`（发送）、`maplibrx:`（接收）、`maplibini:`（注册段）

## 15. 风险与未决问题

1. **隧道带宽**：整库首次拉取不现实 → 必须选择性子集（已在 §11 结论）
2. **大厅帧大小**：块从 512 B 提到 2 KB 需要实测；若丢帧，靠 `LIBDONE` 缺失重发兜底
3. **INI 冲突**：`MentalOmegaMaps.ini` 是全局文件，多方同时改（比如装了别的地图包）会有段重复 → 只做「增删自己这张图的段」，不整文件替换
4. **`.shp/.vxl` 等资源**：部分地图带自定义图形，体积大；白名单要列全，否则同步了 `.map` 却缺素材
5. **旧清单迁移**：`MoLanSyncedMaps.txt` 只记录路径、没有 sha → 首次升级时把「文件当前 sha」当作 base 即可（保守，不会误删）
6. **是否需要「地图库导出/导入 zip」**：对手机用户很实用，可作为 P4 的首项

## 16. 附：为什么不做 objects 目录

Git 用内容寻址存 blob，是为了跨 commit 去重与历史检出。
这里的「历史」只有清单（几十 KB），地图文件本身不需要多版本共存；
一旦复制 blob，一个 3 GB 的库会变成 6 GB+，还会和游戏目录不同步。
因此本项目采用 **「文件就地 + 哈希校验 + 清单/备份」** 的轻量模型，
只在 `MoMapBackup` 里保留最近 3 次覆盖前的副本。
