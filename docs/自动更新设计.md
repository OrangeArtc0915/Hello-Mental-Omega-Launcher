# 自动更新设计（可移植方案）

本文档描述星露谷启动器的「检查更新 + 一键自动更新」是怎么设计和实现的，供同一技术栈（.NET 8 + WPF，自包含单文件发布）的其它程序直接搬用。

实现只集中在少数几个类里，核心是 [LauncherUpdater.cs](../src/StardewLauncher.Core/Updater/LauncherUpdater.cs)。

---

## 1. 适用前提

| 条件 | 说明 |
| --- | --- |
| 技术栈 | .NET 8 及以上，WPF / WinForms 均可 |
| 打包方式 | 自包含单文件（`PublishSingleFile=true`），最终就是一个 `.exe` |
| 发布渠道 | GitHub Releases 和 / 或 Gitee Releases |
| 替换范围 | **只替换 exe 自己**，程序产生的数据（设置、缓存、用户文件）一律不动 |

如果程序不是单文件发布（一堆 dll 一起发），这套方案不适用，得改成"整目录替换"，复杂度高一个量级。

---

## 2. 一句话思路

**程序自己只负责"查版本、下文件、校验"，真正的文件替换交给一个临时 cmd 脚本 —— 它在本进程退出之后才运行。**

这样切分是被 Windows 的规则逼出来的，不是偏好：

1. Windows 不允许覆盖、也不允许删除正在运行的 exe。所以替换动作必须发生在进程退出之后。
2. 不想为了更新额外带一个 updater 程序（用户可能只拷走了主程序，updater 就丢了）。`cmd.exe` 是系统自带的，一定能用。
3. 更新失败必须让用户看见。所以脚本失败时会留一个标记文件，由下次启动的新程序读出来翻译成中文弹窗。

主链路：

```
检查版本 ──► 挑资产 ──► 下载成 .new ──► 校验 ──► 写临时 cmd ──► 本进程退出
                                                                    │
                        ┌───────────────────────────────────────────┘
                        ▼
              脚本：等进程退出 ──► 备份旧文件 ──► 新文件就位 ──► 启动新版本 ──► 删备份与脚本
                                        └── 失败 ──► 回滚 + 写标记（下次启动告知用户）
```

## 3. 六个环节

### 3.1 版本来源唯一

版本号只在 [AppInfo.cs](../src/StardewLauncher.Core/App/AppInfo.cs) 里定义一处，界面、文档、构建脚本都引用它。

```csharp
public const string Version = "1.6.1";
public const string VersionDisplay = "v1.6.1";
public const string GitHubUrl = "https://github.com/<owner>/<repo>";
public const string GiteeUrl  = "https://gitee.com/<owner>/<repo>";
```

注意两点：

- 不要用 `Assembly.GetName().Version` 取版本。单文件发布下容易和真实版本脱节，而且会让"版本号只有一处"这条约定失效。
- 用 `-p:Version=<值>` 把同一个常量传给 `dotnet publish`，保证文件属性里的版本号与常量一致。

版本比较用 [SemVer.cs](../src/StardewLauncher.Core/Smapi/SemVer.cs) 的 `SemVer.IsNewer`，tag 先规范掉前缀（`v1.5.0` → `1.5.0`）。

### 3.2 检查新版本（双源 + 自动回退）

入口是 `LauncherUpdater.CheckAsync()`：按设置里选的线路优先，另一个源兜底，两个都取不到就返回带 `Error` 的结果（**不抛异常**，检查失败绝不能打扰启动）。

两个源的取法不同，都是刻意的：

**Gitee** — 用官方 API，但要查两次：

```
GET https://gitee.com/api/v5/repos/{owner}/{repo}/releases/latest          → tag_name、id、body
GET https://gitee.com/api/v5/repos/{owner}/{repo}/releases/{id}/attach_files → 附件列表
```

`releases/latest` 返回的 `assets` 是自动生成的源码包，**不是人上传的附件**，所以附件必须单独查一次。

**GitHub** — 走网页，不走 API，避开未认证请求 60 次/小时的限流：

```
GET https://github.com/{owner}/{repo}/releases/latest
    → 取 302 的 Location，从 "/tag/v1.6.1" 里切出 tag

GET https://github.com/{owner}/{repo}/releases/expanded_assets/{tag}
    → 用正则 href="([^"]*/releases/download/[^"]+)" 抠出资产名和下载地址
```

两个坑：

- `expanded_assets` 片段里的 `href` 是**根相对路径**（`/owner/repo/releases/download/...`），不补成绝对地址下载器会直接报错。
- 下载器的 `HttpClient` 必须声明支持 gzip / deflate / brotli。GitHub 对不带 `Accept-Encoding` 的请求会直接返回 **500**，表现为"检查更新失败"。

### 3.3 挑资产（必须卡死命名约定）

`PickAsset` 的规则：

1. 优先找**裸的单文件 exe**：以约定前缀开头、以 `.exe` 结尾（`StardewLauncher.exe`、`StardewLauncher-v1.6.0-win-x64.exe`）。
2. 没有裸 exe 时才退一步用整包 zip：同样前缀、`.zip` 结尾。
3. **绝不认"随便哪个 .exe / .zip"**。发布页上可能同时挂着安装器、依赖包之类的无关文件，拿错的结果就是把自己替换成别的程序。

前缀是常量 `ExePrefix`，移植时改成自己程序的名字。

### 3.4 下载与校验

- 下载到 `目标.exe.new`；如果是 zip，下成 `目标.exe.new.zip`，用 `ZipFile` 解出里面的 exe 到 `.new`，然后立刻删掉 zip。
- 下载走 [ResumableDownloader.cs](../src/StardewLauncher.Core/Nexus/ResumableDownloader.cs)：先探测服务器是否支持 `Range`，支持且文件够大就分片并发，中断后能从断点续；不支持就退回单连接。
- 下载前先删掉上次的 `.new` / `.new.zip` 残留。残留存在时"下载成功"可能只是假象。
- 校验两条，都过不了就当下载失败：
  - **文件大小 ≥ 5 MB** —— 单文件自包含 exe 有上百兆，明显偏小说明下到的是重定向页或错误页；
  - **文件头是 `MZ`** —— 真正的 PE 可执行文件。

### 3.5 交棒给脚本

`WriteInstallScript` 生成 `%TEMP%\{name}-update-{pid}.cmd`，`StartScript` 用 `cmd /c` 无窗口启动它，然后调用方**立刻退出进程**（调用 `Application.Current.Shutdown()`；界面侧先 `await Task.Delay(600)` 让状态文字有机会刷新，实际等待由脚本负责）。

脚本用 `tasklist /FI "PID eq {pid}"` 轮询等进程退出，比固定 `timeout` 可靠 —— 只有进程真的不在了，文件锁才会释放。等待上限 90 秒，超时写标记 `timeout` 退出，**此时不动任何文件**。

### 3.6 替换（脚本逐段说明）

脚本是整套方案的核心，完整内容如下（`{pid}` 等占位符由生成时替换）：

```bat
@echo off
setlocal enabledelayedexpansion
set "TARGET=<目标 exe 绝对路径>"
set "STAGED=<目标 exe>.new"
set "BACKUP=<目标 exe>.old"
set "NOTE=<目标 exe>.update-failed.txt"
set /a WAIT=0

:wait
tasklist /FI "PID eq {pid}" 2>nul | find "{pid}" >nul
if errorlevel 1 goto ready
set /a WAIT+=1
if !WAIT! GEQ 90 goto timeout
ping -n 2 127.0.0.1 >nul
goto wait

:timeout
> "%NOTE%" echo timeout
del /f /q "%~f0" >nul 2>&1
exit /b 2

:ready
set /a TRY=0

:swap
set /a TRY+=1
attrib -r -h -s "%TARGET%" >nul 2>&1
attrib -r -h -s "%STAGED%" >nul 2>&1
attrib -r -h -s "%BACKUP%" >nul 2>&1
del /f /q "%BACKUP%" >nul 2>&1
if exist "%BACKUP%" goto retry
move /y "%TARGET%" "%BACKUP%" >nul 2>&1
if exist "%TARGET%" goto retry
move /y "%STAGED%" "%TARGET%" >nul 2>&1
if exist "%STAGED%" goto rollback
goto done

:rollback
if exist "%TARGET%" goto retry
move /y "%BACKUP%" "%TARGET%" >nul 2>&1
if not exist "%TARGET%" goto broken
goto retry

:retry
if !TRY! LSS 5 (
  ping -n 2 127.0.0.1 >nul
  goto swap
)

> "%NOTE%" echo locked
if exist "%TARGET%" start "" "%TARGET%"
del /f /q "%~f0" >nul 2>&1
exit /b 1

:broken
> "%NOTE%" echo broken
del /f /q "%~f0" >nul 2>&1
exit /b 3

:done
start "" "%TARGET%"
ping -n 4 127.0.0.1 >nul
del /f /q "%BACKUP%" >nul 2>&1
del /f /q "%~f0" >nul 2>&1
exit /b 0
```

设计要点：

| 要点 | 原因 |
| --- | --- |
| 先清属性再删/移（`attrib -r -h -s`） | 文件可能是只读或带隐藏属性，直接 `del` / `move` 会失败 |
| 删不掉旧备份就换名重试 | `.old` 可能被残留进程或杀软占着，死磕一个名字会让整个替换卡住。程序侧用 `PickBackupPath` 依次挑 `.old1`…`.old4` |
| **成功判据是"待安装的那份有没有被搬走"** | `if exist "%STAGED%"` 才算没就位。只看 `target` 存在会误判成成功 |
| 失败回滚 | 新文件没就位就把备份换回去，绝不留下"什么都没有"的状态 |
| 最多 5 次重试，间隔 1 秒 | 杀软扫描刚下载的文件会短暂占用，等一会儿就过得去 |
| 失败留标记（`locked` / `timeout` / `broken`） | 没有标记的话，失败只表现为"更新完还是旧版本"，用户和开发者都会误判 |
| 标记只写 ASCII | cmd 的 `echo` 按控制台代码页写字节，直接写中文会乱码。中文文案放在程序里翻译 |
| 成功后 `start` 新版本再删备份 | 保证用户看到的是新版本；备份删除失败也不影响使用 |

### 3.7 启动时收尾

程序启动时（`OnStartup`，越早越好）做两件事：

1. `LauncherUpdater.CleanupStaleFiles()` —— 清掉上次留下的 `.new`、`.new.zip`、`.old`、`.old1`…`.old4`。清理失败只记日志，那些文件常常被杀软占着，过几次启动就清掉了。
2. `LauncherUpdater.TakePendingFailureNote()` —— 读走并删除失败标记，翻译成中文提示用户，然后**跳过本次自动检查更新**（刚失败过，立刻再弹一次提示没意义）。

顺序上要注意：检查更新要在主窗口创建之后再做。WPF 里主窗口是 `StartupUri` 在 `OnStartup` 返回之后才建的，所以用 `Dispatcher.BeginInvoke(DispatcherPriority.ApplicationIdle, ...)` 让出一轮消息循环，那时弹窗才有 owner，位置和焦点才正常。

## 4. 文件与命名约定

| 文件 | 用途 | 生命周期 |
| --- | --- | --- |
| `<name>.exe` | 运行中的程序 | 永久 |
| `<name>.exe.new` | 下载好的新版本，等替换 | 替换成功后消失 |
| `<name>.exe.new.zip` | 下载中的整包（只在用 zip 时出现） | 解出 exe 后立刻删 |
| `<name>.exe.old`（及 `.old1`…`.old4`） | 替换前的旧版本备份 | 新版本启动成功后删 |
| `<name>.exe.update-failed.txt` | 替换失败的标记（内容为 ASCII 标记词） | 下次启动读走即删 |

**这些文件全都紧挨着 exe 放**，不放在 `%TEMP%` 或 `AppData`：替换是同一个卷内的 `move`，同卷移动是元数据操作，比跨卷拷贝快得多，也不会因为目标目录只读而失败。

## 5. 发布侧约定

### 5.1 tag 规范

统一 `v<主>.<次>.<修订>`，例如 `v1.6.1`。程序侧会去掉 `v` 前缀再比较，所以 tag 必须能被规范成纯数字版本号。

### 5.2 资产命名

| 资产 | 命名 | 作用 |
| --- | --- | --- |
| 单文件 exe | `<prefix>.exe` 或 `<prefix>-v<版本>-win-x64.exe` | 首选，下载后直接替换自己 |
| 整包 zip | `<prefix>-v<版本>-win-x64.zip` | 备选，程序解出里面的 exe 再替换 |

命名必须以约定前缀开头，否则不会被识别为可自动更新的资产。

### 5.3 两个源传法不同

| 源 | 传什么 | 原因 |
| --- | --- | --- |
| GitHub | zip **和** 裸 exe | 单个资产上限 2 GB，无所谓；有裸 exe 时优先用它，省一次解压 |
| Gitee | **只传 zip** | 单个附件上限 100 MB，一百多兆的单文件 exe 传不上去 |

这就是为什么下载侧必须支持 zip：不是为了压缩率，是为了绕过 Gitee 的附件上限。

### 5.4 构建命令

```bat
dotnet publish src\<项目>.csproj -c Release -r win-x64 --self-contained true ^
    -p:PublishSingleFile=true -p:DebugType=none -p:Version=<版本号> -o publish
```

版本号从 `AppInfo.cs` 读出来传给 `-p:Version`，保证两处一致。

| 弹窗样式 | 用自绘弹窗（本项目是 `StyledDialog`），不要用 `MessageBox`，否则风格与主界面不一致 |

## 7. 铁律

1. **失败必须留痕。** 没有标记文件时，替换失败只表现为"更新完还是旧版本"，会被误判成"没检查到新版本"，白排查很久。这条最值钱。
2. **脚本里只写 ASCII 标记。** 中文交给程序翻译，避免控制台代码页导致乱码。
3. **做替换的是"正在运行的那一版"的代码。** 所以替换逻辑的修复天然滞后一版才生效；旧版本用户若带着旧脚本的 bug，只能靠手动下载救。
4. **更换 exe 前先确认没有同名进程在跑。** Windows 不让覆盖运行中的 exe，旧文件也删不掉。程序侧提前用 `OtherInstanceRunning`（比对 `MainModule.FileName`）拦下来，别让用户白等一百多兆的下载。
5. **检查更新失败要静默。** 网络问题不该打扰启动，只记日志。
6. **不要把所有 `.exe` / `.zip` 都当更新包。** 只认约定前缀，否则会把程序替换成发布页上的安装器或依赖包。

## 8. 关于进程僵死

实测遇到过一种情况：替换反复失败，最后发现是一个**僵死进程**（`tasklist` 里还有，但线程数 0、内存 0 MB）占着 exe。这种进程不是正常退出，脚本等不到它消失，替换也就永远失败。

处理方式：

- 程序侧 `OtherInstanceRunning` 会在下载前拦住这种情况，提示用户先关掉。
- 用户侧遇到持续失败，重启一次电脑最干脆。

## 9. 怎么验证

不要直接拿正式版本试。本地造一个"旧版本"，指向线上新版本，观察能不能升上去：

1. 把 `AppInfo.Version` 临时改成低一版（例如线上是 `1.6.1`，本地改成 `1.5.0`）。
2. 发布一个单文件 exe，放到一个**独立目录**（例如 `publish\Test-v1.5.0\`），不要覆盖正式目录。
3. 在它的数据目录里放一份设置，打开"启动时自动检查更新"。
4. 启动 → 应弹出发现新版本的确认框 → 点"现在更新" → 观察是否自动退出、替换、并且**自己重新打开**成新版本。
5. 验证完记得把 `AppInfo.Version` 改回去。

要专门验的失败路径：

| 场景 | 怎么造 | 期望 |
| --- | --- | --- |
| 备份文件被占 | 手动占住 `.old` | 自动换名成 `.old1`，替换仍成功 |
| 替换时文件被锁 | 替换期间用别的进程占住 exe | 重试 5 次后回滚，旧版本被重新打开，并写 `locked` 标记 |
| 进程不退出 | 让脚本等一个不退出的 PID | 90 秒后写 `timeout` 标记，**不动任何文件** |
| 下载到坏文件 | 把下载地址指向一个 HTML 或小文件 | 校验拦截，提示"不像是启动器"，不进入替换 |
| 上次失败过 | 手工写一个 `locked` 标记文件 | 下次启动弹中文提示，并跳过自动检查更新 |
